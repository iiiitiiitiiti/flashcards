## 002. IndexedDB は例外が抜けても中止されない。失敗したら明示的に `abort()` する

- 日付: 2026-08-27（2026-08-27 に真因を訂正。旧題「要求と要求の間で `await` しない」）
- 対象: `src/db.ts`（`runAtomically` と、それを使う `saveReview` / `undoReview`）

### 背景

`undoReview` を「進捗を戻す → ログを消す」の順に `await` を挟んで書いていた。
**ログ削除だけを失敗させる注入試験で、進捗だけ巻き戻ってログが残る半端な状態を実際に作れた**（進捗 5→4 件、ログ 5 件のまま）。

当初これを「`await` を挟むとその隙間でトランザクションが自動確定するから」と説明したが、**この説明は誤り**だった。
素の IndexedDB で機構だけを切り出して測った結果は次のとおり。

| 書き方 | 結果 |
| --- | --- |
| `await put(a); await put(b);` | **両方コミットされる**（要求どうしの間の `await` では確定しない） |
| `await put(a); await setTimeout(0); await put(b);` | `InvalidStateError`。`a` は残る（**IDB 以外を待つと**確定する） |
| `await put(a);` のあとに例外を投げて抜ける | **`a` はコミットされる** |

注入試験で踏んだのは3行目である。真因は `await` の位置ではなく、
**例外が抜けてもトランザクションは中止されず、成功済みの要求はそのままコミットされる**こと。
「同一トランザクションだから原子的」は、失敗時に `abort()` を呼んで初めて成り立つ。

もう1つ、`idb` の `tx.done` は**トランザクション生成時に作られる**（`cacheDonePromiseForTransaction`）。
`await tx.done` に辿り着く前に中断されると、その拒否を誰も受け取らず未処理の rejection になる。

### 決定

複数ストアの更新は `runAtomically(tx, issue)` に通す。

1. `tx.done` を**最初に掴み**、要求と一緒に `Promise.all` で待つ
2. 要求は `issue` の**中で**作る（引数で作ると、生成時の例外が `abort` の外へ抜ける）
3. `issue` は受け取った `add` で**作った端から登録する**（まとめて返すと、2つ目の生成で例外が出たとき1つ目の Promise が迷子になり、`abort` の `AbortError` が未処理になる）
4. 失敗したら `tx.abort()`、そのうえで `Promise.allSettled` で後始末してから投げ直す

### 比較した代替案

- 却下: **順番に `await` したまま、失敗時に手で戻す補償処理を書く** — 補償処理自体が失敗しうる。原子性を諦めた時点で、どこまで戻ったかを追う状態がもう1つ増える
- 却下: **ストアごとにトランザクションを分け、失敗したら片方を戻す** — 上と同じ。分けた時点で原子性が無い
- 却下: **要求の間の `await` を消すだけ**（当初の修正）— 症状は消えるが真因ではない。`abort()` を足したことが効いていた。同じ勘違いのまま他の箇所を「安全」と判断してしまう
- 却下: **要求の配列を `issue()` から返す形** — 2つ目の生成で例外が出ると1つ目が迷子になる。注入試験で `AbortError` の未処理 rejection を実際に観測した
- 採用: `runAtomically`（`tx.done` を先に掴む＋生成即登録＋`abort`＋`allSettled`）

### 影響範囲

- `saveReview` と `undoReview` の両方。**`saveReview` には旧来の書き方が残っていた**（Codex レビューの指摘で発見）。毎回の評価が通る主経路なので、こちらの方が露出は大きかった
- `importBackup` は**取り込み全体が1トランザクション**で、途中で失敗すれば自動的に中断されるため意図どおり（部分適用にならない）
- 今後、複数ストアを1トランザクションで触る箇所は `runAtomically` を通す

### 検証

`IDBObjectStore.prototype` の `put` / `delete` を `reviewLog` に限って例外にする注入試験（preview + Playwright）。

- `saveReview`: 注入時 **進捗3/ログ3 のまま変化なし**、「進捗を保存できませんでした」を表示、**未処理 rejection 0件**。復旧後の評価は 4/4 で成功
- `undoReview`: 注入時 **4/4 のまま変化なし**、「評価の取り消しを保存できませんでした」を表示、**未処理 rejection 0件**。復旧後の取り消しは 3/3 へ正しく戻る
- 修正前（配列を返す形）では `AbortError` の未処理 rejection が1件出ていた

**判断が間違いだったとわかる条件**: 保存の失敗後に、進捗とログの件数が食い違う。または `unhandledrejection` が出る。
