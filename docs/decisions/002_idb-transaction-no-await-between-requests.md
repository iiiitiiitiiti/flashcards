## 002. IndexedDB の複数ストア更新では、要求と要求の間で `await` しない

- 日付: 2026-08-27
- 対象: `src/db.ts`（`undoReview`。同じ形の `saveReview` などにも当てはまる）

### 背景

`undoReview` を「進捗を戻す → ログを消す」の順に `await` を挟んで書いていた。
**ログ削除だけを失敗させる注入試験で、進捗だけ巻き戻ってログが残る半端な状態を実際に作れた**（進捗 5→4 件、ログ 5 件のまま）。

IndexedDB のトランザクションは、保留中の要求が無くなった時点で自動的に確定する。
`await` を挟むとその隙間でマイクロタスクへ制御が戻り、**次の要求を出す前に確定してしまう**ことがある。
「同一トランザクションだから原子的」という前提が、書き方次第で崩れる。

### 決定

複数ストアを1トランザクションで更新するときは、

1. 要求を**すべて出してから** `Promise.all` で待つ（要求と要求の間で `await` しない）
2. 失敗したら `tx.abort()` で巻き戻す
3. 中断によって残りの要求が `AbortError` で落ちても、**未処理の rejection にしない**（各要求と `tx.done` に `catch` を付ける）

### 比較した代替案

- 却下: **順番に `await` したまま、失敗時に手で戻す補償処理を書く** — 補償処理自体が失敗しうる。原子性を諦めた時点で、どこまで戻ったかを追う状態がもう1つ増える
- 却下: **ストアごとにトランザクションを分け、失敗したら片方を戻す** — 上と同じ。分けた時点で原子性が無い
- 却下: **`tx.abort()` だけ足して `await` の順番はそのままにする** — 確定済みのトランザクションは中断できない。実際に半端な状態が残ったのはこの経路
- 採用: 要求をまとめて出す＋`abort`＋rejection の後始末

### 影響範囲

- `saveReview`・`importBackup`・`publishDeckCache` など、**複数ストアを1トランザクションで触る箇所すべて**に同じ注意が要る
- 既存コードでは `importBackup` がループ内で `await` しているが、これは**取り込み全体が1トランザクション**で、途中で失敗すれば自動的に中断されるため意図どおり（部分適用にならない）

### 検証

- `IDBObjectStore.prototype.delete` を `reviewLog` に限って例外にする注入試験
  - 修正前: 進捗だけ巻き戻り、ログが残る。エラー表示なし
  - 修正後: **DB は一切変わらない**。「評価の取り消しを保存できませんでした」を表示。復旧後の再試行は成功。page error 0件

**判断が間違いだったとわかる条件**: 保存の失敗後に、進捗とログの件数が食い違う。
