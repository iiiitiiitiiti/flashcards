## 006. デッキの追加・削除を、GitHub を先・端末を後の順で行う

- 日付: 2026-08-28
- 対象: `src/github.ts`（`createDeck` / `deleteDeck`）、`src/db.ts`（`deleteDeckLocalData`）、
  `src/ModalSheet.tsx`（新規）、`src/backup.ts`（`downloadBackup`）、`src/App.tsx`、
  `src/DeckDetailView.tsx`、`src/styles.css`、`scripts/sync-decks.mjs`

### 背景

トークンを登録していればカードは足せるのに、**デッキそのものは GitHub 上でしか作れなかった**。
iPhone だけで完結させたいという要望。削除は取り消せないので、順序と後片付けの範囲に判断が要る。

### 決定

#### 1. 追加は `sha` なしの PUT

`writeDeck` は「最新の `sha` を取ってから PUT」する更新専用の経路。新規作成では `sha` を渡さない。
既にファイルがあると GitHub が **422** を返すので、画面側の重複チェックをすり抜けても止まる。

2026-08-28 に一時ブランチ `api-probe` を切って実 API で確認した（確認後にブランチごと削除。main は無傷）:

| 操作 | 結果 |
| --- | --- |
| 新規ファイルへ `sha` なし PUT | 201 Created |
| 既存ファイルへ `sha` なし PUT | 422 `"sha" wasn't supplied.` |
| 存在しないファイルの GET | 404 |
| `sha` つき DELETE | 200 |
| 同じ `sha` でもう一度 DELETE | 404 |

#### 2. 削除は「GitHub が先、端末が後」

逆順だと、GitHub 側が失敗したときに**進捗だけ消えて戻せない**。GitHub は履歴から復元できるが、
端末の学習記録はどこにも残っていない。失って困る方を後に回す。

#### 3. 404 は「すでに消えている」として成功扱いにする

GitHub 側だけ成功して端末の後片付けが失敗すると孤児レコードが残る。素直に「もう一度削除」を
押したときに `getDeckContents` 相当が 404 を例外にすると、**端末の後片付けへ辿り着けない**。
そこで `deleteDeck` は 404 を成功として返し、後片付けだけを再試行できるようにした。
`deleteDeckLocalData` は冪等（消えていれば何もしない）。

#### 4. `reviewLog` は「読み取りで鍵を集めてから、読み書きで一括削除」

`cardProgress` / `cardNotes` / `hiddenCards` には `byDeck` インデックスがあるが、
**`reviewLog` には無い**（`byReviewedAt` のみ）。カーソル走査が要る。

一方 `runAtomically`（`docs/decisions/002`）は「要求を**同期的に**出し切る」契約なので、
`await` を挟むカーソル走査とは噛み合わない。そこで2段構えにした:

1. 読み取り専用のトランザクションでカーソルを回し、`deckId` の一致する `reviewId` を集める
2. 集めた鍵と他4ストアの削除を、1つの読み書きトランザクションで同期的に出し切る

上限は `REVIEW_LOG_MAX_ENTRIES = 20_000` なので、鍵の配列を持つ程度は問題ない。
1 と 2 の間に新しいログが増える隙間はあるが、削除はカード一覧からしか呼べず、
その間そのデッキを学習していることはない。取りこぼしても孤児が数件残るだけ。

#### 5. 確認はデッキ名の入力で取る

カード一覧の最下部にだけ入口を置く（一覧に置くと誤爆する）。ダイアログでは
何が消えるかを明記し、**デッキ名が一致するまで削除ボタンを押せない**（GitHub の流儀）。
その場でバックアップを書き出せるよう、`SettingsView` に直書きだったダウンロード処理を
`backup.ts` の `downloadBackup()` へ切り出して共有した。

### 比較した代替案

- 却下: **DB を v4 へ上げて `reviewLog` に `byDeck` を足す** — 走査は要らなくなるが、
  移行が全端末に走る。**この機能1つのためにスキーマを動かす価値は無い**
- 却下: **端末側を先に消す** — GitHub 側が失敗したときに進捗だけ失う。取り返しがつかない方を先に消さない
- 却下: **404 を失敗として扱う** — 素直だが、GitHub 側だけ消えた状態から**復旧できなくなる**
- 却下: **一覧から直接削除できるようにする** — 手数は減るが、取り消せない操作を一覧の
  タップ圏内に置かない
- 却下: **削除の取り消しを用意する** — GitHub の履歴からデッキは戻せるが、端末の進捗は戻らない。
  中途半端に「取り消せます」と約束しない
- 却下: **デッキ id（＝ファイル名）の変更** — id は進捗のキーでもある。変えると全カードの進捗が孤児になる
- 却下: **`decks:sync` に「カード id が消えた」判定を足す** — 初版のプランではこれを安全策として
  挙げていたが**誤り**だった。`import-quiz-xlsx.py` は `GENRE_DECKS` の16パスにしか書かないので、
  アプリで足した手動デッキは差分にならない。pull 漏れで実際に起きるのは
  `git push` が非 fast-forward で拒否されることだけで、git が安全に止めてくれる。
  したがって足したガード（`origin/main` より遅れていたら冒頭で停止）は
  **データ保護ではなく「4段目まで進んでから分かりにくく失敗する」のを避けるためのもの**

### 検証

- 実 API（一時ブランチ）: 上表の5挙動
- 単体（`tests/deck-crud.test.ts`）。`deleteDeckLocalData` について4点を見る。
  対象デッキのデータが消えて他デッキは残ること。再実行しても壊れないこと。
  `reviewLog` を走査で拾えること。そして**途中で失敗したら先に成功した削除も残らないこと**
  （`IDBObjectStore.delete` へ例外注入）。
  `createDeck` / `deleteDeck` については、`sha` なし PUT、422 の翻訳、規約外 id の通信前停止、
  sha を取ってからの DELETE、404 では DELETE を打たないこと、403 を失敗として伝えること
- 変異試験。`abort()` の除去、`deckCache` 削除の除去、404 早期 return の除去、`sha` の混入。
  4つとも対応するテストが落ちた
- ブラウザ（`npm run preview`・390×844）。トークン無しでは追加・削除の入口が出ない。
  3種類の入力検証は通信前に止まる。作成後はカード一覧へ遷移する。
  削除はデッキ名が一致するまで押せない。削除完了で端末の5ストアが消え、他デッキは無傷。
  **403 では端末データが残りダイアログは開いたまま。404 では DELETE を打たず後片付けだけ走る。**
  `quiz-` のデッキには再生成の警告が出る
- `sync-decks.mjs` のガード。使い捨ての git リポジトリで、遅れていれば終了コード1で停止し、
  `git pull --ff-only` 後は通過した
- Codex 指摘の修正ぶん（テストは 194 件から **200 件**へ）。404 の3分岐、`importDrafts` の削除、
  読み取り中止時に未処理 rejection を残さないこと、追い越された取得がキャッシュを書かないこと
- 変異試験の追加4件。世代ガードの除去、`publishDeckCache` 前の判定の除去、404 の権限確認の除去、
  `importDrafts` 削除の除去。いずれも対応するテストが落ちた
- ブラウザで再起動の再開を確認。孤児レコードと「削除中」の印を仕込んで読み込み直すと、
  IndexedDB の4ストアと出題タグの記憶が消え、印も外れた。
  `setItem` を観測して、印が**後片付けの前に立ち、終わってから外れる**ことも確かめた

### Codex レビューで入れた修正（2026-08-28）

初版（`3b5eec0`）を Codex にレビューさせたところ、**不可逆な削除としては穴が残っていた**。
指摘は全部ソースで裏を取り、6件を反映した。

#### P1: 404 を無条件に「削除済み」と扱っていた

GitHub は**権限が足りないときも 404 を返す**（リソースの存在を漏らさないため）。
確かめずに削除済みと決めつけると、GitHub にデッキが残ったまま端末の進捗だけ消えて戻せない。
これは、この設計がいちばん避けたかった事態そのものだった。

`assertDeckReallyMissing` を足し、`testConnection` でリポジトリが見えて書き込めることを確かめてから
「無いのはファイルの方だ」と判断する。追加の API 呼び出しは 404 のときだけで、通常の削除では増えない。

#### P1: 削除に追い越された取得がキャッシュを書き戻していた

削除前から走っていた `refreshSnapshot` が後から着地すると、古い一覧で `publishDeckCache` してしまう。
消したデッキが、進捗だけ失った「新規デッキ」として復活する。
初版では削除後に `refresh()` を呼んでいたが、**それは順序の保証になっていない**。

`snapshot.ts` に世代番号を持たせた。取得の開始時に採番し、`invalidateSnapshotFetches()` か
後続の取得で追い越されたら、キャッシュを書かず `null` を返す。呼び出し側もその結果を捨てる。
デッキの作成・削除の直後に `invalidateSnapshotFetches()` を呼ぶ。作成側にも同じ競合があった。

#### P1: 再起動をまたぐ後片付けができなかった

GitHub の削除に成功したあと、端末の後片付けの前にアプリが落ちると孤児レコードが残る。
同じ id で作り直すと、古い進捗が新しいデッキへ再接続されてしまう。
初版の「もう一度削除を押せばやり直せる」は、アプリが開いたままのときにしか効かない。

`localStorage` へ「削除中」の印を残す。GitHub の削除が成功した直後に立て、後片付けが終わったら消す。
起動時は `resumePendingDeckDeletions()` が印を見てやり直す。
印を立てるまでの窓は文1つ分しかないので、取りこぼしはほぼ起きない。

#### P2: `importDrafts` と出題タグの記憶が消えていなかった

`importDrafts` は `deckId` を持つが削除対象から漏れていた。同じ id で作り直すと、
前回の CSV インポートが「未完了」として蘇る。`flashcards:study-tag:<deckId>` も残っていた。
消すものが IndexedDB と localStorage にまたがるので、`src/deckcleanup.ts` に窓口を1つ作ってまとめた。

#### P2: 読み取りトランザクションの `tx.done` を回収していなかった

`runAtomically` と同じ理屈で、読み取り中に例外が出ると `readTx.done` の AbortError が
未処理の rejection になる。注入試験で再現させてから `readAtomically` を足した。
書き込みの前に止まるのでデータは失われないが、失敗時の始末として不完全だった。

#### P2: バックアップ中に削除できた

`exportBackup` はストアごとに別トランザクションで読むので、書き出しの最中に削除が走ると
「進捗はあるがログは無い」半端なバックアップになりうる。書き出し中は削除ボタンを無効にした。

#### 見送った指摘

- **大規模削除の分割トランザクション化** — Codex は数万〜10万件規模を懸念したが、
  そこは**実機で測らないと閾値が決められない**。憶測で設計を変えず、未検証として残す（下記）

- iPhone 実機での見た目とキーボード挙動。Playwright は Chromium だけなので再現できない。
  入力欄を持つシートは `ModalSheet` で画面上部に置いてあるが、実機での確認は未了

  1トランザクションで同期発行する設計のままなので、実機で 20k / 50k / 100k 程度を測って、
  UI の停止・メモリ圧迫・`AbortError` が出ないかを見る必要がある（Codex 指摘）
